🔍 What is CSRF?

One sentence: CSRF forces a logged-in user’s browser to send a forged request to a vulnerable website — changing email, password, or transferring funds without the victim knowing.

⚡ Key limitation: CSRF is one-way — attacker can’t read the response. It only triggers actions, not data theft.

⚙️ How CSRF works (step by step)

  1. Victim logs into bank.com → session cookie stored in browser.
  2. Attacker crafts a malicious page with a hidden form or image tag that submits a request: POST /transfer?to=attacker&amount=1000.
  3. Victim visits attacker’s page (e.g., fake ad, phishing link).
  4. Browser automatically includes the session cookie → the bank processes the request as if it came from the victim.
✅ Remember: The server only checks the session cookie, not where the request came from → that’s the vulnerability.

✅ Conditions for CSRF

  • Victim has an active session on the target site.
  • The action is state-changing (POST, PUT, DELETE, or GET that modifies data).
  • No origin validation or anti-CSRF token.

🎯 Where to look for CSRF (attack surface)

Focus on requests that change something important:

  • Change email / password
  • Add admin user / change privileges
  • Money transfer, purchase, refund
  • Delete account or post
  • Update security settings
  • Enable 2FA / disable 2FA
🚨 Myth: POST = safe → No! CSRF works with POST, GET, PUT, any method if origin isn’t verified.

📄 Building a CSRF Proof of Concept (simple HTML)

1. POST-based CSRF (classic hidden form)

<html>
<body>
  <form action="https://target.com/change-email" method="POST" id="csrf">
    <input type="hidden" name="email" value="hacker@evil.com">
  </form>
  <script>document.getElementById("csrf").submit();</script>
</body>
</html>

If the target uses GET for sensitive actions, an image works even easier:

<img src="https://target.com/delete-account?confirm=yes" width="0" height="0">

🔓 Bypassing CSRF tokens (real world)

Many apps add anti-CSRF tokens, but they’re often misconfigured.

1. Token validation only on POST → switch to GET

Change POST to GET in Burp, move parameters to URL. If request succeeds → CSRF via GET.

<img src="https://target.com/change-email?email=attacker@evil.com">

2. Remove token entirely

If token parameter is optional, just delete it from the request. Some apps validate only if token exists.

3. Token not tied to session (global token)

Log into your own account, grab a valid CSRF token, use it in forged request against victim → works if token is not per-user.

4. Weak / predictable token

Token might be base64(role) or timestamp. Decode and forge.

# example: token "YWRtaW4=" decodes to "admin" → easily guessable

5. Double-submit cookie bypass

App compares csrf cookie with body param. If you can set a cookie via CRLF injection or subdomain, set both to same value.

<img src="https://target.com/search?q=%0d%0aSet-Cookie:csrf=fake%3bSameSite=None">
<form><input name="csrf" value="fake"> ... </form>

🍪 SameSite cookie bypasses (modern CSRF)

SameSite=Lax blocks cross-site POST but allows top-level GET. SameSite=Strict blocks everything.

When SameSite=Lax (Chrome default)

  • GET-based CSRF: if the action accepts GET → still vulnerable.
  • Method override: use _method=POST parameter — browser sends GET (allowed), server treats as POST.
  • 2-minute window: Chrome treats cookies without SameSite as Lax, but first 2 minutes after setting, POST is also allowed. Force OAuth login to refresh cookie → exploit quickly.
<form action="https://target.com/change-email" method="GET">
  <input name="email" value="attacker@evil.com">
  <input name="_method" value="POST">
</form>
<script>document.forms[0].submit();</script>

When SameSite=Strict (bypass via redirect gadget)

Find open redirect or path traversal that leads to sensitive endpoint. The final request is same-site → cookie sent.

<form action="https://target.com/redirect?next=/my-account/change-email?email=evil@x.com">...</form>
🔥 Subdomain XSS = same-site → bypass Strict as well. If you find XSS on cms.target.com, you can send authenticated requests to target.com.

🚫 Bypassing Referer headers

  • Drop Referer: Use <meta name="referrer" content="no-referrer"> to remove header. If server validates only when present → bypass.
  • Spoof with domain in URL: If server checks that Referer contains target.com, put target.com in your URL query and set referrer policy unsafe-url.
<meta name="referrer" content="unsafe-url">
<script>history.pushState('','','/?target.com');</script>

📋 Testing checklist (run on each state-changing endpoint)

  • No CSRF token at all? → simple POC works.
  • Remove token param entirely → still accepted?
  • Change POST → GET (also try PUT/DELETE).
  • Replace token with random value → bypass?
  • Use your own token from another account → not tied to session?
  • Check token pattern: base64? md5 of user id? predictable?
  • Check SameSite attribute on session cookie (Strict / Lax / None).
  • If Lax: test with GET form (or method override).
  • If Strict: search for open redirect, path traversal, or XSS on sibling domain.
  • Referer validation? Try remove header; try spoof with target domain in URL.
  • Check WebSockets: CSWSH (session cookie + no origin check) → hijack WS.
  • Look for CRLF injection that sets cookies (csrfKey, csrf token).

🛡️ Mitigations (for devs — but we test against them)

  • Anti-CSRF tokens: per-session, unpredictable, tied to user session, validated server-side.
  • SameSite=Strict on session cookies (or Lax as fallback).
  • Custom request headers (X-CSRF-Token) — cannot be set cross-origin without CORS.
  • Origin / Referer validation (whitelist your own origin).
  • Re-authentication for critical actions (e.g., require password again).
